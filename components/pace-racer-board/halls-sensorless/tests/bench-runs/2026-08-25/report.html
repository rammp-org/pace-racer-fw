Ethernet & RTPS telemetry on the 20 kHz FOC loop

Host-side tests run against PR #11 on the real motor-control board, motor idle and spinning under load. Speed regulation is untouched by saturating traffic — but the delivered rate falls off a cliff above 485 Hz with no error reported, and it took an espp bug fix before a subscriber could receive anything at all.

Two corrections to earlier findings

An earlier pass ran against the wrong firmware

The board arrived carrying an older build; the reflash inside sweep_endpoints.py is what actually installed the PR build, partway through the session. It was caught because rtpstat printed the field names parts=/eps= — a string that does not exist anywhere in the PR binary (strings on the flashed image finds only wmatch=/rmatch=).

Those results are discarded. Everything below was measured on firmware verified by boot banner and by string-matching the flashed image. The pre-port build survives in one place only — the engine comparison in Figure 2 — where it is a legitimate before/after baseline and is labelled as such.

"Publishing got 9× cheaper" was measured with nothing listening

Those pub_us figures were taken with no matched reader, so publish() serialized the sample and then transmitted nothing — the writer's proxy list was empty. Comparing that against the pre-port engine, which was transmitting, flattered the new engine.

Figure 2 now uses with-subscriber costs throughout. The real improvement is about 6.7× (3839 µs → 569 µs at 10 Hz), not 9×.

Why nothing was arriving — and whose fault it was

For most of this session rtps_sub.py reported nothing arrived and the board sat at wmatch=0. Two independent causes, and neither is a defect in this PR.

Correct behavior  The board only transmits to matched readers

StatelessWriter::progress() iterates the writer's reader proxies. With none matched the loop body never executes and no packet leaves the board — while pub_ok still counts up, because the publish() call itself succeeded. That is textbook RTPS. 

if (m_proxies.getNumElements() == 0) {
    SLW_LOG("No proxy!");          // logs, then falls through
}
for (const auto &proxy : m_proxies) {
    ...build packet, send...   // never executes with zero proxies
}

The old engine had a use_multicast_for_user_data escape hatch that sprayed user data at the multicast group with no reader required. The upstream espp v1.2.0 rewrite removed it. rtps_sub.py is a passive multicast sniffer that never announces itself, so it is never discovered, so it is never sent anything. The PR ported to that engine; it did not cause this.

espp bug  RTPS multicast ignores the configured interface

Writing a proper DDS subscriber was not enough — it still failed to match. The cause is in espp itself: EsppTransport never passes multicast_interface to the socket layer, on sends or on group joins. On a multi-homed host every RTPS multicast therefore follows the default route. On this Mac that is Wi-Fi, so the subscriber's SPDP announcements went out over Wi-Fi and never touched the bench cable. interface_address was honored for binding and receiving, and silently ignored for transmitting.

The socket layer already supports this and its own documentation describes this exact case — "set it on multi-homed hosts to send multicast out a specific NIC (e.g. wired vs Wi-Fi)". The transport just never wires it up. Invisible on a single-homed Linux CI box; fatal on a developer laptop. A three-line local patch fixed it: 

before — SPDP seen on the wire
  192.168.50.50    BOARD       7 pkts    (host absent entirely)

after
  192.168.50.1     HOST-SUB   14 pkts
  192.168.50.50    BOARD      10 pkts
[RtpsTopicData]: Received unicast locator: 192.168.50.50:7411

With that in place telemetry flows immediately and decodes correctly — state=H, temps=28.0/29.6/30.0/31.0, flux=0.0280, matching the console stream field for field. This is worth reporting upstream: it makes espp's RTPS unusable for host tooling on most developer machines.

The delivery cliff

With a real subscriber attached, delivery is lossless and exact through 300 Hz, and saturates at about 485 Hz. Above that it does not degrade gracefully — it collapses. At 1000 Hz requested the board publishes 535 samples per second and 25 arrive; at 2000 Hz it publishes 734 per second and none arrive at all.

Throughout, pub_fail stays at 0. The firmware believes every publish succeeded. The loss is entirely silent, with no counter anywhere that reveals it.

Publish cost, honestly compared

pub_us is the per-cycle cost of one publish call. Both series below have a matched reader, so both are actually transmitting — which is the only fair comparison, and the one the earlier "9×" figure got wrong.

Coexistence holds — the PR's central claim

Two metrics must be kept apart, and the PR is right to insist on it:

  • coalesce — notifications ÷ task runs. 1.00 means the FOC task never missed a tick. The real "did the control loop keep up" measure.
  • late% — share of current samples where the sampling ISR fired late or overran, so the sample landed outside the PWM null window and was discarded. Signal quality, not control timing.

coalesce held at 1.00 in every condition tested — every publish rate including the collapsed ones, and every network flood level. Publishing at 2000 Hz with 7402 overruns and total delivery failure still did not cost the control loop a single tick.

Read late% within one boot, not across boots

The idle baseline is not stable across reboots — it was 0.2% in one session, 5.0% in another, and 0.4% here, all with the motor idle and nothing on the network. foc_sampler.hpp:543 attributes lates to I2C temperature reads and DRV fault polls preempting the sampling ISR, so it is unrelated to network activity; the phase relationship between those pollers and the ISR appears to be set at boot.

The deltas within a single boot are sound and are what the tables below report. Absolute late% figures should not be compared between runs — including against the PR's 4.9%.

Spinning: speed regulation is untouched

Seven captures of 15 s each at 100 rpm, five free-shafted and two loaded against the magnetic particle brake at ~4 A — the PR's own test condition. Each capture reports the standard deviation of measured speed, of torque current, and the observer's tracking error against the halls.

Speed regulation does not move. Across every condition — quiet, RTPS publishing, inbound flood, and saturating bidirectional traffic while driving under load — rpm standard deviation stays between 0.74 and 0.83. The gap between quiet and fully saturated (0.832 → 0.815, loaded) is smaller than the gap between two identical quiet runs (0.787 vs 0.805). That is the PR's central claim, and it holds.

Worth acting on  The telemetry stream starves under load

The rows/s column shows the CSV stream dropping from 9.9 to 7.3 rows per second under bidirectional traffic — a quarter of the telemetry simply not emitted. This is the stream task sitting at priority 0, the lowest in the system, which the PR's own review notes raise as an open question. It is now measured: the answer is yes, it starves, by about 25% at saturation.

Two caveats on these numbers

  • Absolute rpm sd is ~1.8× the PR's (0.83 vs 0.45) even at the same 100 rpm / 4 A operating point. The hall table was uncalibrated for this session (hs reports cal=0), and rpm_hall — the quantity being averaged — comes from that table. The relative comparison across conditions is unaffected, since every capture shares the same uncalibrated table.
  • The brake stalls far earlier than the bench notes suggest. The stall edge sits between 1.0 V and 1.8 V, not at the ~2.5 V the notes describe: at 1.8 V the rotor stopped outright and the controller reverted from closed-loop sensorless to hall mode with zero current. The loaded captures were taken at 1.2 V, which draws the 4.1 A the PR's condition calls for. Approach that edge from below.

Where the PR's claims still break

Contradicted  Writers cap at four, not eight

The PR states writers "cost about 11.4 ms each per cycle and scale linearly to 8 writers." Neither half survives. Per-writer cost is about 114 µs, a hundredfold difference — and the participant fails to start at five writers or more, leaving up=0 and pub_ok=0.

Stale docs  Discovery works, but not as documented

SPDP announcements arrive and parse, so discovery is healthy. Every identifying field differs from the PR's screenshot, because that screenshot was taken on the old engine.

Test hazard  Stale reader proxies inflate every repeat measurement

Each subscriber run creates a participant with a fresh GUID. Because the topic is BEST_EFFORT with no liveliness timeout, the board keeps the ReaderProxy of every dead subscriber and goes on transmitting to it. A second subscriber then receives duplicates of every sample.

This produced an impossible 18.3 Hz delivered from a 10 Hz request before it was spotted. Any repeated measurement must reboot the board between subscriber lifetimes — the sweep above uses a single subscriber across all nine rates for exactly this reason.

Resolved  The decoder's wire layout

rtps_sub.py assumes 15 contiguous floats then a trailing uint8 state. The wire actually places state in a four-byte slot at offset 4, shifting every later field — so it silently returned flux as temps[0] and a padding byte as state. That script was left unpatched, because it cannot receive anything on this engine anyway; the working subscriber uses the Sample struct directly and lets espp's own reflection handle the layout, which sidesteps the question entirely.

Raw transport beats the documented figures

The W5500 transmit path and USB console are untouched by the RTPS engine change and both exceed the PR's numbers — which already reflect the instruction-cache fix it describes. Host-side capture confirmed zero packet loss at both payload sizes, with the firmware reporting err=0.

An unrecorded finding: inbound is the weak direction

The PR characterises the transmit path in detail but never measures inbound capacity. It is much lower, and collapses with payload size. That matters because the PR names inbound RTPS cost as its biggest unmeasured gap — anything bidirectional hits this ceiling first.

What is still open

The spin work is complete. Four things remain unmeasured or unresolved, in rough order of how much they should block merging.

  • The delivery cliff above 485 Hz, and the fact that pub_fail reports nothing when samples vanish. A counter that surfaces the drop would make this diagnosable in the field rather than only on a bench with a subscriber attached.
  • Participant start fails at five or more writers, against a documented claim of linear scaling to eight.
  • Inbound RTPS processing cost — still the PR's own biggest stated gap. The host subscriber built for this run is one half of what closing it needs; the other half is an external writer the board can subscribe to.
  • High-power operation. Everything here is at or below 4.1 A and 100 rpm. Switching noise on the current sense rises sharply beyond that, and the PR is explicit that its own envelope stops in the same place.

Two housekeeping items also worth folding in: the hall table was uncalibrated throughout (cal=0), which inflates absolute rpm standard deviation; and this firmware has no lim/vds/vl/odg commands, so the bench's documented arm profile cannot be applied — all runs used boot defaults of an 8 A console clamp, 15 A trip and 80 °C limit.

Abbreviations

RTPS / DDS
Real-Time Publish-Subscribe, the wire protocol under the DDS middleware standard. The board publishes telemetry as a DDS participant.
SPDP
Simple Participant Discovery Protocol — the multicast announcements participants use to find each other.
SEDP
Simple Endpoint Discovery Protocol — how a discovered participant declares its individual readers and writers, with the topic, type and address to send to.
ReaderProxy
A writer's record of one matched remote reader. No proxies means no transmission — the writer has nowhere to send.
BEST_EFFORT
QoS with no retransmission or delivery guarantee. Correct for live telemetry, where a late sample is worthless — but it means loss is silent.
XCDR1 / CDR
Common Data Representation, the binary wire encoding DDS uses. Here generated by reflection over the C++ Sample struct.
FOC
Field-Oriented Control — the 20 kHz motor-control loop this work must not disturb.
pub_us
Per-cycle cost of one publish call, microseconds.
pub_ok / pub_fail
Publishes the firmware considers successful / failed. pub_fail stays 0 even when nothing is delivered.
coalesce
Task notifications ÷ task runs. 1.00 means the control task serviced every tick — the true "did the loop keep up" metric.
late%
Share of current samples discarded for landing outside the PWM null window. Signal quality, not control timing. Baseline varies between boots.
cmax
Longest single control-cycle execution time in the window, microseconds.
overrun
Publish cycles where the deadline had already passed — the publisher could not keep up with the requested rate.
wmatch / rmatch
Remote readers matched to local writers, and vice versa. wmatch=0 means published data has nowhere to go.
ISR
Interrupt Service Routine — here, the current-sampling interrupt synchronised to the PWM null window.
pps
Packets per second. Network disturbance tracks packet rate rather than bandwidth.
W5500
The WIZnet Ethernet controller, on SPI2 — the same bus as the DRV8353 gate driver, which is why coupling was a concern.
VM
Motor bus supply, 48 V here. The gate driver will not answer without it.
iq / id
Quadrature and direct axis currents — the torque-producing and flux-producing components in the rotating frame.
Measured 2026-08-24/25 on ESP32-S3 hardware at 48 V, W5500 on the SPI expansion header, point-to-point over a USB dock Ethernet port to a Mac at 192.168.50.1. Firmware identity was confirmed by boot banner and by string-matching the flashed binary before any figure here was recorded. Delivered rates come from a purpose-built DDS subscriber compiled natively from the espp sources, running with a three-line local patch that makes RTPS multicast honor the configured interface; that patch lives in a gitignored directory and does not affect the firmware, which was never reflashed after it was applied.
